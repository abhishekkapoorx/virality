# Design: LinkedIn Agent (Consolidated, Updated)

Generated by /office-hours on 2026-04-27 and updated on 2026-05-03  
Status: DRAFT  
Mode: Startup

## Problem Statement

Busy professionals want consistent, high-quality LinkedIn output, but current creation workflows cause context switching, inconsistent voice, and low repeatability. Full automation increases reputational and governance risk.

## Current Product Thesis

Build an evidence-first, human-in-the-loop LinkedIn drafting loop in Slack, backed by a cloud orchestration service and DB-versioned instruction profiles.

Core experience:

- submit idea in Slack
- receive draft in user voice
- refine/approve in Slack
- publish manually by human

## Demand Evidence Status

Evidence is still interest-level. Weekly dependence, payment intent, and measurable workflow replacement must be proven before expanding to additional channels.

## Target User and MVP Wedge

Initial persona:

- engineering manager/CTO publishing technical leadership content on LinkedIn

MVP wedge:

- transform raw inputs into high-quality drafts in user voice
- run approve/refine/reject loop in Slack
- preserve manual publish only
- prove measurable time savings and acceptance rate

## Scope and Constraints

Non-negotiable constraints:

- human-in-the-loop approval before any publish
- no autonomous LinkedIn posting/actions
- brand/policy guardrails enforced before approval
- optimize for learning speed over broad automation

MVP channel scope:

- in: Slack connector
- out: WhatsApp/Discord until Slack proof gates are met

## Architecture Direction

Selected architecture lane: **one orchestration service + thin channel adapters** (Approach B from extension).

Layers:

- orchestration API (auth, tenant routing, canonical event ingestion)
- workflow engine (deterministic state transitions)
- channel adapters (Slack now, others later)
- web app (onboarding, connector setup, instruction profile management, history)
- storage (drafts, audit logs, encrypted connector secrets, instruction versions)

Channel model:

- each Slack thread maps to internal `conversation_id`
- business logic remains channel-agnostic

## Instruction Profile Source of Truth

Instruction profiles live in product DB with version history (MVP does not depend on external docs).

Behavior:

- profile edited in web
- snapshot version attached at generation time
- metadata stores `instruction_bundle_version`
- on profile-read failure: fallback to last known good snapshot + visible warning

## MVP Workflow Map

1. User submits raw input in Slack (voice note/text/link).
2. System generates draft with style rules and current instruction snapshot.
3. Draft returned in Slack with `Approve / Refine / Reject`.
4. Refine loops regenerate from explicit user deltas.
5. Approve marks post ready; human publishes manually.
6. System logs audit and outcome metrics.

Exception paths:

- generation failure -> retry once -> operator fallback
- style-policy failure -> block approval and request regeneration
- Slack delivery failure -> retry and alert fallback

## Compliance Boundary (MVP)

Allowed:

- AI drafting and regeneration from explicit user inputs
- manual human publish only

Forbidden:

- autonomous posting to LinkedIn
- autonomous comments/replies
- publish without explicit human approval event

Required immutable audit fields:

- approver identity
- approval timestamp
- approved draft hash/version
- prompt/version id
- instruction profile version
- final published URL (when available)

## Success Criteria and Decision Gates

Pilot outcomes:

- >= 5 target users complete >= 2 weekly cycles for 4 weeks
- median draft-to-approval time reduced by >= 50% vs baseline
- draft acceptance rate >= 60% with <= 1 meaningful revision
- quality lift >= 4/5 vs current workflow

Additive reliability gates:

- Slack event processing success >= 99% weekly rolling
- instruction snapshot attached for >= 95% of generations

Decision checkpoints:

- Week 2 continue if: >= 3 active users, time reduction >= 30%, acceptance >= 50%
- Week 4 advance if: >= 5 active users, acceptance >= 60%, revisions <= 1 median, quality >= 4/5

## Metrics and Instrumentation

Capture per cycle:

- `input_received`
- `draft_generated`
- `user_feedback_received`
- `draft_regenerated`
- `approved_for_publish`
- `published_manual`
- `cycle_closed`

Baseline protocol:

- collect last 2 posts per pilot user
- record prep time, iterations, and publish time
- use same quality rubric in baseline and pilot

## Distribution and Operating Model

Distribution:

- managed private pilot in one niche
- Slack is canonical execution surface
- web app handles config, connector setup, instructions, logs

Operations:

- generation fallback: operator -> founder backup
- policy exceptions: reviewer -> founder backup
- Slack outage: ops owner -> engineering on-call
- release gate: founder -> delegated product lead

## Dependencies

Must-have now:

- pilot cohort definition and sourcing
- baseline measurement protocol
- Slack app + signing/webhook setup
- DB schema for instruction profiles and version history
- secret management (tenant connector tokens)
- prompt/version control and policy checks

Can defer:

- additional connectors
- advanced analytics/dashboarding
- integration marketplace features

## Open Questions

- tenant model for pilots: workspace-first vs user-first
- instruction profile schema depth: freeform vs structured blocks
- behavior when profile changes during active refine loop
- data residency and compliance requirements by pilot region
