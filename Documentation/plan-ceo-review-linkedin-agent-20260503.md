## Landscape check (brief)

**Layer 1 (tried-and-true):** Thought leadership drafting assistants, generic LLM chats, scheduling tools. Human approval before publish is standard for reputation-sensitive users.

**Layer 2 (discourse):** “AI LinkedIn” crowded; differentiation usually fails without wedge persona, workflow fit, or governance story.

**Layer 3 (first-principles):** Your wedge matches a real failure mode: **context switching** and **voice drift**. Multi-channel delivery is only an advantage if **one state machine** and **auditability** stay intact. Risk: connectors multiply operational and compliance surface before demand is proven.

**Eureka hook (conditional):** If interviews show users living in **Slack for team comms** but posting **personal LinkedIn**, the winning UX is “meet them in Slack” plus **persistent instruction profiles**. That is sharper than “another web AI writer.” It still requires proof, not assertion.

```
                              │                           │
                              ▼                           ▼
                       ┌────────────┐              ┌────────────┐
                       │ LLM + policy│             │  Postgres   │
                       │  services   │             │  + object   │
                       └────────────┘             │  store audit│
                                                   └────────────┘
```

### Scaling first breakpoint

- **10x:** Slack webhook burst + LLM concurrency + instruction snapshot fan-out. Rate limit and queue **per tenant**.
- **100x:** Token vault, DB connection pool, multi-region, noisy-neighbor isolation (enterprise tier story).

### Single points of failure

- Slack ingress (webhook verification + retries).
- LLM provider outage (graceful degrade: queue + user-visible retry).
- Instruction profile store/read path (fallback: last snapshot).

### Security architecture (high level)

- **Trust boundary:** Web establishes identity and OAuth; Slack signatures verified on ingress; internal service auth (mTLS or signed service tokens) between worker and API if split.

## Section 2: Error and rescue map (registry seed)

| Codepath | What can go wrong | Rescue | User sees |
|----------|-------------------|--------|-----------|
| Slack verify | Bad signature | 401, log tenant unknown | Slack shows retry or silence per Slack UX |
| Slack delivery | 429/5xx | exponential backoff, DLQ | “Temporary issue, try again” |
| LLM call | timeout, empty, refusal | retry once, then escalate operator path | explicit failure message in thread |
| LLM JSON/tool output | malformed structured output | validator rejects, regenerate bounded | “Couldn’t parse action; tap Regenerate” |
| Instruction profile read | timeout/conflict | use last snapshot + banner | “Using last saved instructions” |
| DB write | conflict | idempotent conversation keys | avoid duplicate drafts |

**Critical gap to close in implementation:** define **exception taxonomy** in code (no bare `except Exception` swallowing).

## Section 3: Security and threat model

| Threat | L × I | Mitigation in plan |
|--------|-------|---------------------|
| Forged Slack requests | H × H | Signing secret per workspace, constant-time verify |
| Token theft (Slack OAuth token) | M × H | KMS, encryption at rest, rotation on revoke |
| Cross-tenant data leak | H × H | Tenant id on every query; integration tests for isolation |
| Prompt injection via user paste | M × M | Policy layer + refuse dangerous publish claims; audit |
| Instruction doc poisoned | M × H | Diff snapshots; warn on large deltas; optional approval |
| OAuth phishing clone app | L × H | Verified Slack OAuth branding; domain control |
